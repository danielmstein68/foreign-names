# Decision log

Every analytic decision, in the order it was made. Scripts add to this file automatically through `common.log_decision()`.

- **2026-10-24 · setup:** Use Python 3.11 in `.venv`. *Why:* ethnicolr and its PyTorch dependency need a Python version they support; the system default is 3.13.
- **2026-10-24 · setup:** Use ethnicolr 2.0.0. It is a newer PyTorch rewrite with a different API from the old TensorFlow `pred_wiki_ln`. *Why:* this is the version pip installs. Its Wikipedia surname model has the same 13 categories the spec expected.
- **2026-10-24 · census:** If no raw Census file is placed in `data/raw`, use the 2010 Census surname table bundled inside ethnicolr. *Why:* census.gov is blocked from this environment. The bundled table has 162,253 surnames, matching the official file. Its "(S)" suppressed cells are filled by splitting the leftover percentage equally across the suppressed columns. If the raw file is added, it is preferred and the two are cross-checked.
- **2026-10-24 · names:** Surnames are matched to the Census file as letters A–Z only, with spaces and apostrophes removed (DE LA CRUZ→DELACRUZ, O'BRIEN→OBRIEN). *Why:* that is how the Census file spells them.
  - If that fails for a hyphenated or multi-word name, try the first part, then the last part.
  - Name particles (de, van, St…) are never matched on their own.
  - The matching rule used is recorded for each candidate.
- **2026-10-24 · names:** Suffixes (Jr, Sr, II–V, Esq, MD, PhD) and titles (Dr, Hon, Rev…) are dropped. Nicknames in quotes or parentheses are dropped.
- **2026-10-24 · foreign:** The coding rule is fixed in `docs/foreign_coding_rule.md` before any outcome data is loaded.
- **2026-10-24 · model:** "Number of candidates in the contest" and the nonpartisan flag have the same value for everyone in a race. Contest fixed effects therefore absorb them, so they are not separate controls in the within-contest model. *Why:* they cannot be estimated; listing them as controls would be misleading.
- **2026-10-24 · model:** The main spec uses continuous scores (1 − pctwhite, and P(foreign)). Tercile indicators are a robustness check.
- **2026-10-24 · model:** House standard errors are clustered by state × district number. *Why:* this is the House "jurisdiction". It is approximate because districts are redrawn each decade.
- **2026-10-24 · MIT data:** The MIT House file (`1976-2024-house.tab`, uploaded by Daniel as `mit_house_dataverse_files.zip`) is comma-separated despite its name. Every data row is also wrapped in an extra pair of quotes, and quotes inside fields are backslash-escaped. `src/readers.py` undoes this when it reads the file; the raw file is left as is. *Why:* without the fix, every row loads as one column. The reader refuses to run if any row ends up with the wrong number of fields. All 33,805 rows parse into 20 fields.
- **2026-10-24 · data:** Downloaded the MIT state presidential returns, 1976–2024 (`data/raw/mit_president/`), to use as the baseline for Senate overperformance. No guestbook form was required.
- **2026-10-24 · build/house:** Kept regular general elections only: dropped 98 of 33,805 rows (primaries, runoffs, specials). *Why:* Spec covers general elections; specials have unusual timing and turnout.
- **2026-10-24 · build/house:** Dropped 2,844 write-in rows and 1,280 placeholder rows (OTHER, BLANK, SCATTERING, OVER/UNDERVOTES...). They are excluded from contest vote totals too. *Why:* Spec: exclude write-ins as MIT marks them; placeholders are not candidates.
- **2026-10-24 · build/house:** Combined fusion-ticket lines: 29,583 rows -> 28,093 candidates. *Why:* Spec outcome is candidate vote share, so a candidate's votes on all party lines are summed.
- **2026-10-24 · build/senate:** Kept general elections (stage 'gen'/'GEN'), dropped 15 of 3,945 rows (primaries, runoffs). Senate special elections are KEPT (as separate contests) and flagged. *Why:* Senate specials are mostly held on the November general-election ballot, unlike House specials.
- **2026-10-24 · build/federal:** Incumbency inferred: a candidate is the incumbent if they won the same seat in the previous House election (2 years) or within the previous 6 years for Senate. Match on first name + surname in the same district (any district in the state in redistricting years), or on surname + party in the same district (for nickname changes). A looser first-initial rule was tried first and rejected: it produced false matches (e.g. challenger John T. Anderson vs incumbent John B. Anderson). *Why:* MIT files have no incumbency flag; spec says infer it and say so. Misses appointed senators and members first elected in a special election.
- **2026-10-24 · build/local:** Office types ['City Council', 'Mayor', 'School Board'] coded nonpartisan; County Legislature, County Executive, Sheriff and Prosecutor coded partisan. *Why:* HKS has no ballot-type flag (checked readme). Office type is the agreed proxy; it is wrong for some states (e.g. partisan city elections in some places), stated as a limitation.
- **2026-10-24 · build/local:** Vote share recomputed as votes / sum of votes in the contest, not taken from HKS's vote_share column. *Why:* HKS vote_share does not always sum to 1 within a contest.
- **2026-10-24 · model (agreed with Daniel, before any results):** For partisan races (House, Senate, local partisan), the main outcome becomes **overperformance**: a candidate's vote share minus their party's presidential vote share in the same place (state for Senate, county for local partisan, district for House if a source is found). The spec's version (raw vote share with a party control) is kept as a comparison. *Why:* minority-named Democrats run disproportionately in Democratic districts. A single party control cannot absorb how party strength varies by district, so it would bias the name estimate toward zero or positive.
- **2026-10-24 · model (agreed with Daniel):** Also run a **swing ("shift") design** for partisan races: the change in a party's vote share in the same district from one election to the next, compared with how the candidate's name scores changed. *Why:* it uses only data we already have, and each district acts as its own baseline, so no presidential vote data is needed. This matters most for House, where district-level presidential returns are not available to us.
- **2026-10-24 · build:** Correction: an earlier quick count reported 8,200 House contests. The correct figure is 10,860 (435 per cycle). The quick count silently dropped rows whose "runoff" field was blank.
- **2026-10-24 · score:** Surnames parsed from the full candidate name with src/names.py for all sources, instead of using HKS's own lastname column. *Why:* Same rule everywhere. Where the two disagree (0.7% of local rows) ours is usually right: HKS splits 'van Bramer' -> 'bramer', 'St Lawrence' -> 'lawrence', and has junk like 'name)'.
- **2026-10-24 · build/senate:** Dropped 469 write-in rows and 187 placeholder rows. *Why:* Same rule as House.
- **2026-10-24 · build/local:** Dropped 18 placeholder rows ('scattering', 'write-ins'...). *Why:* Same rule as House and Senate; they are vote totals, not candidates.
- **2026-10-24 · mena (Daniel approved, before any results):** Added an exploratory Middle Eastern / Muslim-origin name indicator. The rule and hand review are in `docs/foreign_coding_rule.md` and `docs/mena_name_review.csv`. *Why:* Census codes these names as white, so they are a sharper test of H2 than German names. The sample is small (189 candidates), so it is pooled-only and exploratory.
- **2026-10-24 · checkpoint (Daniel's reaction):** The checkpoint showed that the main rule's "white & foreign" cell is mostly German and Scandinavian names. Both foreign rules (main and sensitivity) will be reported as headline results.
- **2026-10-24 · regress:** Local candidates with missing incumbency (18%) are kept, with incumbent set to 0 and a missing-incumbency indicator added. *Why:* Dropping them would lose many contests; the indicator stops the fill-in from biasing the incumbency coefficient.
- **2026-10-24 · regress:** For local partisan races, the party control is HKS's estimated party (pid_est: D/R/unknown), because HKS does not record the ballot party. *Why:* It is the only party information available for local races; it is an estimate, not the label voters saw.
- **2026-10-24 · regress:** Overperformance baseline is the party's share of the presidential vote (of all votes cast) in the most recent presidential election in or before the race's year: state level for Senate, county level for local partisan (2000+, 5-digit county FIPS only). Only Democrats and Republicans enter this design. *Why:* Matches the candidate vote-share outcome, which is also a share of all votes.
- **2026-10-24 · regress:** Swing design: House and Senate races with exactly one scored Democrat and one scored Republican; Democratic two-party share on (Democrat score − Republican score), with district × redistricting-cycle fixed effects (state for Senate), year fixed effects, and both incumbency flags. Not run for local partisan races. *Why:* District-cycle effects make each district its own baseline. Local districts can't be followed reliably over time in HKS.
- **2026-10-24 · regress:** Pooled models allow party effects to differ by source (party × source dummies). *Why:* The contest fixed effect already absorbs source.
- **2026-10-24 · quadrants (after Daniel asked how the four groups perform):** Each group is compared with "white & not foreign" within the same race, using the checkpoint's top-tercile groups for the main rule. For the sensitivity rule, top-tercile cut-offs put Johnson, Brown and Miller in the "foreign" groups, so that rule's groups use the yes/no score instead: foreign = most likely origin outside British/German/French/Nordic. *Why:* the change is based on the misclassified name lists, not the estimates. Note: this analysis was run after the step-5 results had been seen.
- **2026-10-24 · robustness:** Open-seat check: contests where no candidate is flagged as incumbent. For local races, missing incumbency counts as not incumbent here. *Why:* Simple rule; incumbency is missing for 18% of local candidates.
- **2026-10-24 · robustness:** Multi-seat races: outcome = 100 × votes × seats / total votes in the race, with the same within-race model. *Why:* Plain vote share is not comparable across races with different numbers of seats. 100 means exactly the pace needed to win a seat.
- **2026-10-24 · co-ethnic test (Daniel asked, after the main results):** Added an exploratory test of co-ethnic voting. The full rules are in `docs/coethnic_test.md`, written before any demographic data was loaded. *Why:* it could explain why Garcia-type names show no penalty on average while Hansen-type names do.
